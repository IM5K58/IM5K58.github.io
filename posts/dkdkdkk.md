## 0. 큰그림 잡기 (1)

**Docker를 공부하는 목적은 보통 이 셋 중 하나이다.**

* **내 앱을 어디서나 똑같이 실행하고 싶다**
* **개발 환경 세팅 지옥에서 벗어나고 싶다**
* **배포와 서버 운영을 더 예측 가능하게 만들고 싶다**

Docker는 이 문제를 해결하려고 등장했다.

Docker가 공개되기 전까지의 핵심 문제는 “서버에 코드를 옮겨 실행하는 일이 너무 어렵다”는 것이었다.

Docker는 2013년 PyCon에서 처음 공개되었고, 이후 컨테이너 사용을 대중화했다.

## 1. 사전 개념 (1)

> [!TIP]
> ## 1. Docker 전에 반드시 알아야 하는 최소 사전지식

먼저, 컨테이너에 대해서 짚고 넘어가보자.

**컨테이너(Container):** 항구에 있는 거대한 화물선과 네모난 철제 '컨테이너'를 떠올려 보라. 컨테이너 안에는 옷, 가전제품, 식량 등 무엇이든 넣을 수 있지만, 겉보기에는 똑같은 네모난 상자이다. 그래서 배, 트럭, 기차는 내용물에 상관없이 규격화된 컨테이너만 쉽게 옮기면 된다.

**소프트웨어에서의 컨테이너:** **프로그램과 그 프로그램이 실행되는 데 필요한 모든 것(설정 파일, 라이브러리 등)을 모아 하나의 상자(컨테이너)에 포장하는 기술이다.** 가상 머신처럼 무거운 운영체제를 통째로 포함하지 않고, 딱 프로그램 실행에 필요한 것만 담기 때문에 아주 가볍고 빠르다.

**요약하자면:** 도커(Docker)는 바로 이 '컨테이너'라는 네모난 상자를 아주 쉽고 편리하게 만들고, 옮기고, 실행할 수 있게 도와주는 세계에서 가장 유명한 **컨테이너 관리 프로그램이**다.

---

Docker를 이해하려면 먼저 **프로그램**과 **프로세스**를 구분해야 한다.

* **프로그램**: 디스크에 저장된 실행 파일
* **프로세스**: 지금 실제로 실행 중인 프로그램

Docker 컨테이너는 “작은 가상컴퓨터”가 아니라, 본질적으로 ***호스트 위에서 격리되어 실행되는 프로세스이다. **`*호스트 = 진짜 바탕이 되는 컴퓨터, 실행의 주체.`

Docker를 처음 배울 때 생기는 가장 흔한 오해는

“컨테이너 = VM 같은 완전한 별도 컴퓨터”라고 생각하는 것이다.

그보다는 격리된 실행 환경을 가진 프로세스의 묶음이라고 이해하는 편이 정확하다.

조금 더 쉽게 풀어쓰자면,

**내 실제 컴퓨터(또는 실제 서버) 안에서 돌아가긴 하는데,
그 프로세스가 자기만의 독립된 공간에서 도는 것처럼 보이게 만든다는 것이다.**

컨테이너는 결국 **프로세스이다.**

예를 들어 Node 서버를 Docker로 실행하면,

**사실은 호스트 OS가 그 Node 프로세스를 실행하고 있는 것이다.**

다만 그냥 평범하게 실행되는 게 아니라, Docker가 그 프로세스를 특별히 감싸서

* 보이는 파일 범위
* 보이는 네트워크
* 보이는 프로세스 목록
* 쓸 수 있는 메모리/CPU

이런 걸 제한하고 분리하는 것이다.
그래서 **호스트에서 실행되지만, 자기만의 작은 세계에서 실행되는 것처럼 보이는 것이다.**

---

컨테이너는 자기만의 파일시스템 뷰를 가진다.

이게 뭔뜻이냐? 컨테이너 별로 확인할 수 있는 파일들의 경로를 다르게 설정해줄 수 있다는 것이다.

Docker는 이미지와 컨테이너 파일시스템을 바탕으로 실행 환경을 만들고, Dockerfile은 그 파일 구성을 정의한다.

---

Docker 컨테이너는 기본적으로 네트워크를 가지고 있고, 포트 매핑을 통해 호스트와 통신한다.

컨테이너는 자신이 어떤 종류의 네트워크에 붙어 있는지 알지 못하고, 단지 자기 인터페이스·IP·게이트웨이·DNS 등을 보게된다.

그래서 결국, 

* **컨테이너 내부의 **`localhost`
* **내 컴퓨터의 **`localhost`

이 둘은 같은 게 아니다.
컨테이너 내부에서 `localhost`는 **그 컨테이너 자신**을 뜻하는 것이다.

> [!TIP]
> ## 2. 가상화와 컨테이너의 차이

**가장 먼저, VM은 무엇인가?**
VM은 **하드웨어를 가상화**해서 그 위에 **완전한 OS 전체**를 올린다.

그래서 VM마다 자기 커널이 있고, 그만큼 무겁다. 

**그러면, 컨테이너는 무엇인가?**
컨테이너는 **OS 레벨 격리이다.**

여러 컨테이너가 같은 호스트 커널을 공유하면서, 프로세스·파일시스템·네트워크가 분리된 것처럼 보이게 한다. 그래서 보통 VM보다 가볍고 빠르다.


쉽게 설명하자면,

**VM은 컴퓨터 안에 새로운 컴퓨터를 하나 더 만드는 것이고,**

**컨테이너는 컴퓨터 안에서 프로그램 마다 돌아갈 독립된 공간을 만들어주는 것이다.**

* **VM = 집을 통째로 새로 하나 더 짓는 느낌**
* **컨테이너 = 같은 큰 건물 안에 방을 나눠 쓰는 느낌**

그래서 VM은 하나의 컴퓨터 안에서 여러 개의 가상 컴퓨터를 만들고, 각 VM마다 자기 운영체제와 설정을 따로 가질 수 있다. 대신 무겁고 느릴 수 있다. 

컨테이너는 호스트의 커널을 공유하면서, 독립된 실행 환경처럼 분리된 여러 프로세스를 돌릴 수 있다. 그래서 더 가볍고 빠르다. 

아래 그림으로 더 명확하게 이해해보자.

```
VM 구조

[실제 컴퓨터]
 └─ Host OS
     └─ Hypervisor
         ├─ VM 1
         │   ├─ Guest OS
         │   ├─ 라이브러리
         │   └─ 앱
         └─ VM 2
             ├─ Guest OS
             ├─ 라이브러리
             └─ 앱
```

```
컨테이너 구조

[실제 컴퓨터]
 └─ Host OS
     └─ Docker Engine
         ├─ Container 1
         │   ├─ 앱
         │   ├─ 필요한 라이브러리
         │   └─ 설정
         └─ Container 2
             ├─ 앱
             ├─ 필요한 라이브러리
             └─ 설정
```

한번 더 요약해서 표현하면,

* **VM = 내 컴퓨터 안에 새 컴퓨터를 또 하나 만든다.**
* **컨테이너 = 내 컴퓨터 안에서 프로그램만 독립 공간에 넣어 실행한다. (Python 하나, MySQL하나 등..)**

**이 차이를 이해하면 아래 현상이 납득된다.**

* 컨테이너는 부팅 시간이 매우 짧다
* 컨테이너는 OS 전체가 아니라 앱 실행에 집중한다
* 컨테이너는 커널을 공유하므로 VM과 보안/격리 모델이 다르다
* Mac/Windows에서는 리눅스 컨테이너를 돌리기 위해 보이지 않는 Linux VM이 끼어든다

여기서 한가지 더 짚고 넘어갈건, 
컨테이너라는 생각은 오래전부터 있었고, Docker가 그것을 **대중적이고 실용적인 개발 workflow**로 바꿨다는 것이다. 

> [!TIP]
> ## 커널이란?

**커널은 운영체제의 핵심 관리자**이고,

**컨테이너는 그 하나의 커널을 같이 쓰면서도, 각 프로세스가 서로 다른 세상을 보는 것처럼 만들어진 구조라고 생각하면 된다.**

컴퓨터의 구조를 조금 뜯어서 보면 다음과 같다.

```
[사용자 / 앱]
 - 크롬
 - VSCode
 - Python
 - Node
 - MySQL

[커널]
 - CPU 관리
 - 메모리 관리
 - 파일 접근 관리
 - 프로세스 관리
 - 네트워크 관리

[하드웨어]
 - CPU
 - RAM
 - 디스크
 - 네트워크 카드
```

즉,

* **앱은 그냥 자기 마음대로 하드웨어를 직접 만질 수 없음**
* 중간에서 **누가 CPU를 얼마나 쓰는지**
* **누가 파일을 읽을 수 있는지**
* **누가 포트를 열 수 있는지**
* **누가 메모리를 얼마나 쓸지**

이런것들을 관리하는 게 바로 **커널**이다.

한번 더 요약해서 말하자면,

**커널 = 컴퓨터의 총관리자**

앱들은 직접 하드웨어를 만지지 않고, 항상 커널에게 부탁해서 일을 처리하도록 되어있다.

그래서 VM은 다음과 같은 느낌으로 생각하면 된다.

```
VM 1 -> Guest OS 1 -> Kernel 1
VM 2 -> Guest OS 2 -> Kernel 2
```

각 VM마다 자기 운영체제가 있고, 자기 커널이 있다.

그런데 컨테이너는 다음과 같다.

```
Container 1 -> 앱
Container 2 -> 앱
Container 3 -> 앱
        ↓
   하나의 Host Kernel 공유
```

즉, 컨테이너마다 커널이 따로 있는 게 아니라 **호스트의 커널 하나를 다 같이 사용하는 것이고, 이래서 가벼운 것이다.**

그럼 왜 커널을 공유하는 데, 설정이나 파일들이 안섞일까?

커널은 모든 것들을 한곳에 풀어서 관리하는 얘가 아니고,

각각의 프로세스에 관해 필요한 만큼 배분해주면서 관리하는 얘다.

* 너는 이 프로세스들만 봐
* 너는 이 파일시스템만 봐
* 너는 이 네트워크만 써
* 너는 메모리 여기까지만 써

이런식으로..

그래서 커널은 하나지만, 각 컨테이너 입장에서는 독립된 공간처럼 느껴지는것이다.

정리하자면, 

* **커널은 컴퓨터 자원을 관리하는 핵심 관리자다.**
* **컨테이너는 각자 커널을 따로 가지지 않고, 호스트 커널을 공유한다.**
* **커널이 보이는 세계와 자원 한도를 다르게 설정해줘서 컨테이너가 독립된 것처럼 보인다.**

> [!TIP]
> ## 그럼, 결국 왜 사람들이 Docker를 많이 쓸까?

예를 들어 웹 프로젝트가 있다고 해보자.

이 프로젝트를 실행하려면:

* Node 20 필요
* npm 버전 맞아야 함
* 특정 라이브러리 필요
* 환경변수 필요

이걸 사람마다 직접 설치하면 컴퓨터마다 다 달라진다.

이때 나오는 말이 바로 다음의 명대사이다.

“내 컴퓨터에선 잘 되는데요?”

Docker는 이러한 문제가 생기는 것을 방지한다.

왜냐면 아예 실행 환경 자체를 컨테이너로 통째로 묶어서 배포하기 떄문이다.

즉:

* 앱
* 라이브러리
* 실행환경

을 하나의 상자처럼 만들어서 어디서든 비슷하게 실행하게 해주는 것이다.

Docker = 컨테이너를 다루는 도구 중 하나라고 생각하면 된다.

이건 VM도 가능하지만, VM은 너무 무겁기 때문에 앱 배포에는 컨테이너가 훨씬 실용적이다.

## Docker의 핵심 개념 (1)

docker를 사용하는 근본적인 이유: 

**내 컴퓨터에선 잘되는데요? 를 해결 하기 위함.**

1. **프로그램 실행 환경의 문제**

개발자가 자신의 노트북에서 열심히 만든 프로그램(웹사이트 등)을 서비스하기 위해 실제 운영 서버로 옮기면, 갑자기 에러가 나면서 실행되지 않는 경우가 많다. 

1. **가상 머신(VM, Virtual Machine)**
하나의 큰 컴퓨터 안에 윈도우 컴퓨터 1대, 리눅스 컴퓨터 1대를 가상으로 만들어 각각 독립적으로 돌리는 거죠. 하지만 이 방식은 **운영체제(OS)를 통째로 설치해야 하므로 무겁고, 느리고, 컴퓨터 자원을 너무 많이 차지**한다는 단점이 있다.

이때 등장한 개념이 바로 컨테이너 이다.

**컨테이너(Container):** 항구에 있는 거대한 화물선과 네모난 철제 '컨테이너'를 떠올려 보라. 컨테이너 안에는 옷, 가전제품, 식량 등 무엇이든 넣을 수 있지만, 겉보기에는 똑같은 네모난 상자이다. 그래서 배, 트럭, 기차는 내용물에 상관없이 규격화된 컨테이너만 쉽게 옮기면 된다.

**소프트웨어에서의 컨테이너:** **프로그램과 그 프로그램이 실행되는 데 필요한 모든 것(설정 파일, 라이브러리 등)을 모아 하나의 상자(컨테이너)에 포장하는 기술이다.** 가상 머신처럼 무거운 운영체제를 통째로 포함하지 않고, 딱 프로그램 실행에 필요한 것만 담기 때문에 아주 가볍고 빠르다.

**요약하자면:** 도커(Docker)는 바로 이 '컨테이너'라는 네모난 상자를 아주 쉽고 편리하게 만들고, 옮기고, 실행할 수 있게 도와주는 세계에서 가장 유명한 **컨테이너 관리 프로그램이**다.



> [!TIP]
> ## 도커를 사용하는 이유 (장점)

1. **너무 가볍고 빠름**
도커 컨테이너는 운영체제를 새로 켜는 것이 아니라, 컴퓨터의 핵심 기능은 공유하면서 내 프로그램만 쏙 실행하기 때문에 **1초 만에 프로그램이 켜지고 꺼진다.**
1. **완벽한 독립성과 격리**
   도커를 쓰면 A 프로그램과 B 프로그램을 각각 다른 컨테이너 상자에 담아서 실행하기 때문에, 한 컴퓨터 안에서도 서로 전혀 간섭하지 않고 운영된다.
1. **배포와 확장이 너무나 쉽다.**
   도커를 사용하면 미리 만들어둔 컨테이너를 실행시키면 되기 떄문에 쉽다.
2. **환경의 일관성**
   도커의 가장 큰 존재 이유이다. 개발자의 노트북, 테스트용 컴퓨터, 아마존(AWS)이나 구글 클라우드 서버 등 어디든 **도커만 설치되어 있다면** 똑같은 환경에서 프로그램이 완벽하게 실행



> [!TIP]
> ## 핵심 개념 - 도커,도커 이미지,도커 허브, Dockerfule, docker-compose

#### 1. 도커 이미지

**도커 이미지는** 프로그램이 실행되는 데 필요한 모든 것(프로그램 코드, 라이브러리, 설정 파일 등)을 꾹꾹 눌러 담아 놓은 **'설계도'**이자 **'원본 틀'**이다.

**특징은 다음과 같다.**

1. 불변성 : 한 번 만들어진 이미지는 수정할 수 없다.
2. 스스로 실행되지 않는다 : 미지는 그 자체로 작동하는 프로그램이 아니라 작동할 준비를 마친 '파일들의 묶음’
3. 공유하기 쉽다 : 이미지만 보내주면, 누구든 똑같은 환경에서 실행 가능

#### 2. 도커 컨테이너

** 도커 컨테이너는 도커 이미지(틀)를 바탕으로 실제로 컴퓨터 메모리에 올라가서 실행되고 있는 프로그램이라고 생각하면 된다.**

특징은 다음과 같다.

1. 여러 개를 만들 수 있다 : 컨테이너는 무수히 많이 만들어낼 수 있다.
2. 상태가 변하고, 쓰고 지울 수 있다 : 실행 중인 상태에서 안에 새로운 데이터를 저장할 수도 있고, 필요 없어지면 언제든지 삭제할 수 있다. 
3. 독립성: 각각의 컨테이너는 서로 전혀 영향을 주지 않고 독립적으로 돌아간다.

**즉, 도커 컨테이너는 껍데이기이고, 도커 이미지는 해당 컨테이너를 채울 속재료 내지 기능들이라고 생각하면 된다.**

#### 3. 도커 HUB

**스마트폰에 새로운 앱을 깔고 싶을 때 구글 플레이스토어나 애플 앱스토어에 들어가는 것처럼, 도커 이미지가 필요할 때는 도커 허브(Docker Hub)를 이용한다.**

특징은 다음과 같다.

1. 전 세계의 수많은 개발자와 회사들이 자신들이 만든 도커 이미지를 무료로 올려두고 공유하는 거대한 온라인 창고이다.
2. 공식 이미지 제공 : 우분투(Ubuntu), 파이썬(Python), 자바(Java), MySQL(데이터베이스) 같은 유명한 소프트웨어들은 해당 개발사에서 직접 공식 이미지를 올려준다.
3. 시간 단축: 가 처음부터 바닥부터 환경을 세팅할 필요 없이, 내 입맛에 맞게 살짝만 고쳐 쓰면 되기 때문에 개발 속도가 엄청나게 빨라진다.

#### 4. Dockerfile

도커 허브에서 남이 만든 이미지를 가져왔다면, 이제 거기에 '내가 만든 코드'를 넣어서 나만의 고유한 이미지로 만들기 위해 사용하는 파일.

메모장 같은 텍스트 파일에 도커가 이해할 수 있는 명령어를 순서대로 적어둔 문서이다.

비유하자면 다음과 같다.

우분투 OS를 깔아라 -> 파이썬을 설치해라 -> 내 코드를 복사해 넣어라 -> 코드를 실행해라 

라는 식의 내용을 적어놓으면,

`docker build` 라는 명령어 입력 시도커가 이 과정(Dockerfile)을 위에서부터 아래로 쭉 읽으면서 지시사항대로 실행한다. 

그러면 나만의 도커 이미지가 만들어지는 것이다.

Dockerfile 예시

```markdown
# 1. 밀가루 준비 (기본 운영체제와 파이썬 환경 가져오기)
FROM python:3.9-slim

# 2. 작업할 도마 세팅 (컨테이너 안에서 작업할 기본 폴더 지정)
WORKDIR /poetry_app

# 3. 레시피 북 가져오기 (필요한 외부 라이브러리 목록 복사)
COPY requirements.txt .

# 4. 재료 손질하기 (목록에 있는 라이브러리들 설치)
RUN pip install -r requirements.txt

# 5. 내가 만든 팥 앙금 넣기 (내 컴퓨터에 있는 진짜 프로그램 코드들을 전부 복사)
COPY . .

# 6. 오븐 스위치 켜기 (컨테이너가 켜질 때 마지막으로 딱 한 번 실행할 명령어)
CMD ["python", "app.py"]
```

#### 5. Docker Compose

하나의 프로그램(예: 웹사이트)이 제대로 돌아가려면 보통 하나의 컨테이너만으로는 부족하다.


웹 서버를 돌리는 컨테이너 1개, 회원 정보를 저장하는 데이터베이스(DB) 컨테이너 1개 등 **여러 개의 컨테이너가 동시에 필요**한 경우가 대부분이다.

Docker Compose는 
여러 개의 도커 컨테이너를 **하나의 그룹(세트)으로 묶어서 한 번에 켜고 끌 수 있게 해주는 도구이다.**


만약 컨테이너가 3개라면, 매번 `docker run` 명령어를 엄청나게 길고 복잡하게 3번이나 입력해야 한다.
하지만 `docker-compose.yml` 이라는 파일에 "A 컨테이너(웹)와 B 컨테이너(DB)를 이 설정대로 같이 묶어서 실행해 줘!"라고 한 번만 적어두면 바로 한번에 명령어를 통해 실행 가능하다.

`docker-compose up`

`docker-compose down`

docker-compose.yml 예시

```markdown
version: '3.8' # 도커 컴포즈의 버전

services:
  # 첫 번째 메뉴: 시집 웹사이트 서버
  web:
    build: .                 # 현재 폴더에 있는 Dockerfile을 읽어서 이미지를 만들어라!
    ports:
      - "80:5000"            # 외부에서 80번으로 접속하면, 컨테이너 안의 5000번으로 연결해줘!
    depends_on:
      - database             # 데이터베이스가 먼저 켜진 다음에 웹 서버를 켜줘!

  # 두 번째 메뉴: 회원과 시를 저장할 데이터베이스
  database:
    image: postgres:13       # 도커 허브에서 남이 만들어둔 공식 DB 이미지를 그대로 가져와라!
    environment:
      POSTGRES_DB: poetry_db
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: password123
```

이 파일을 만들고 터미널에 명령어 `docker compose up`** 을 입력하면**

* 도커가 알아서 DB 이미지를 다운로드해서 켜고,
* 내가 만든 웹사이트 코드를 컨테이너로 만들어준 다음,
* 이 두 개를 네트워크로 연결해서 동시에 실행해 준다.
